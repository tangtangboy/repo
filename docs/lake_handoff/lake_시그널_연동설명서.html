LAKE · INTEGRATION GUIDE · V1

시그널을 받고,
실제 체결을 돌려보내는 방법

lake(가명) strategt와 상대 매매 서버를 연결하기 위한 개발자 설명서입니다. 신호 전달과 체결·포지션 회신을 따로 연결해야 대시보드에서 실제 보유 현황을 볼 수 있습니다.

현재: 로컬 기록 전용 회신 수신기 구현 · 실제 연동 미완료
상대 수신 주소와 공개 회신 주소는 미정입니다. 실제 시크릿·계정 연결은 설정하지 않았으며, 이 수신기에는 주문·신호 발송·거래소 조회 기능이 없습니다. 발신 신호 규격은 협의안입니다.
연결 흐름상대 준비받는 신호돌려보낼 회신표시 기준테스트 순서전달 요청문

1. 연결 흐름

① 우리 → 상대: 매매 신호우리 전략이 신규 진입·추가 진입·부분 청산·전량 종료·보호가격 변경을 상대의 HTTPS 주소로 전달합니다. 발신기 미구현 · 규격 협의
② 상대 → 우리: 실제 결과상대가 신호 접수, 주문 제출, 체결·거부·취소와 전체 포지션 현황을 회신합니다. 대시보드는 이 회신을 표시합니다. 로컬 수신기 구현

차트의 백테스트 거래와 상대 계정의 실제 체결은 별개입니다. 과거 차트 표시는 발송 대상이 아니며, HTTP 2xx 접수도 실제 주문이나 체결을 뜻하지 않습니다.

2. 상대 개발자가 먼저 준비할 것

  1. 주문을 실행하지 않는 HTTPS 테스트 수신 주소를 알려주세요. lake 전용 경로인지, 기존 ZigZag 경로를 재사용할지도 확정합니다.
  2. 두 방향의 인증 키를 안전하게 교환할 방법을 정합니다. 방향별 키를 분리하고 회신용 TEST/LIVE 키도 서로 다르게 만듭니다. 실값은 메신저 본문·화면·소스·로그에 넣지 않고 각 서버의 비공개 .env에 보관합니다.
  3. 분할 체결·추가 진입·부분 청산·롱/숏 헤지·보호가격 변경 지원과 전략별 수량 귀속 방법을 확인합니다. Bybit가 같은 방향 포지션을 합산해도 상대의 원장에서 기본·횡보·과열 몫을 구분해야 합니다.
  4. 실제 체결 회신 기능을 구현합니다. Bybit 실제 체결 자료를 근거로 결과를 보내고, 30초마다 완전한 포지션 스냅샷을 보냅니다. 주문 체결 또는 보호가격 변경 직후에도 전체 스냅샷을 갱신합니다.
  5. 연결 중단·오류 시 조치를 정합니다. 신규 처리 중지, 미처리 작업 확인·취소, 기존 보호주문 유지, 대사 후 수동 재개 절차를 합의합니다. 실제 발송·실거래는 별도 승인 전까지 활성화하지 않습니다.
기존 대화의 마지막 “연동 완료·6건 HTTP 200”은 ZigZag의 당시 기록입니다. 그 규격의 close는 종목 전량 청산입니다. lake의 부분 익절을 기존 close로 보내면 안 됩니다.

3. 상대가 받을 매매 신호 협의안 · 발신 코드 없음

대상은 Bybit / linear / BTCUSDT, 수량은 BTC, 가격은 USDT입니다. 전략 코드는 basic(기본), overheat(과열), range(횡보)로 구분합니다.

action의미와 상대 처리
entry지정 전략·포지션·레그 신규 진입.
add지정 포지션에 qty_btc만큼 추가. 반복 이벤트도 고유 ID로 구분.
partial_exit지정 포지션 몫에서 명시 BTC 수량만 감소. reduceOnly, 전량 청산으로 변환 금지.
full_exit지정 전략 포지션·레그의 잔량 종료. 다른 전략이나 반대 레그까지 종목 전량 청산하지 않음.
protection_update보호가격 변경, protection_revision 증가. qty_btc:null. 실제 적용 결과 회신.

event_id는 재전송에도 불변이며, event_sequence는 position_id별 증가합니다. 신호의 reference_price는 참고 가격이고 실제 체결가는 아닙니다. expected_qty_btc_after는 처리 후 기대 잔량입니다. 퍼센트 수량 해석은 사용하지 않습니다.

상대는 신호의 유효시간·중복·순서·수량을 검증하고 영속 접수 후 5초 안에 2xx를 반환합니다. 예제의 15초 유효시간, 재시도·손절 미확인 시 정책 등은 최종 합의 대상입니다. mode:test는 기록만 하며 주문을 실행하지 않습니다.

4. 상대가 돌려보낼 체결 회신 구현된 수신 규격

로컬 수신 주소: POST http://127.0.0.1:8766/api/execution-report
대시보드 조회: GET http://127.0.0.1:8766/api/execution-state

127.0.0.1은 우리 컴퓨터 내부 주소입니다. 상대 서버가 접근할 공인 HTTPS 회신 주소는 별도로 배포·합의해야 합니다. 현재 외부에 공개되지 않았습니다. 공개 시 POST 회신 경로만 노출하고, 상태 조회는 로컬에서만 사용합니다.

인증·저장

헤더필수 값
Content-Typeapplication/json. 압축 본문 불허, 본문 최대 65,536바이트.
X-Signaturehex(HMAC-SHA256(secret, raw_body)), 소문자 16진수 64자리. 받은 원본 바이트로 검증하며 JSON 재직렬화 금지.
X-TimestampUnix 밀리초. 본문 ts와 정확히 일치, 수신 시각에서 ±60초 이내.
회신 키LAKE_REPORT_SECRET_TEST, LAKE_REPORT_SECRET_LIVE. 서로 다른 최소 32바이트 값. 정적 웹 폴더 밖의 .env에서만 읽으며 운영체제 환경변수·명령 인자로 받지 않음.
운영 상태LIVE 키가 없으면 화면은 미연동. 해당 mode 키가 없으면 POST 503. TEST 보고는 LIVE 포지션·체결 화면에서 제외.

보고서는 비공개 SQLite에 영속 저장합니다. 계정 식별자 필드는 받지 않습니다. 실제 주문·체결 ID는 해시 기반 가명으로 바꾼 뒤 저장·표시하며 원본 본문·키는 로그에 남기지 않습니다. position_id/event_id/report_id는 계정·개인정보를 포함하지 않는 불투명 ID로 정하세요.

A. 개별 처리·체결 결과 — kind: execution

execution에 신호 event_id, 포지션 position_id, 전략, 방향, position_idx, 동작, 처리 상태를 넣습니다. 같은 event_id의 후속 보고는 같은 포지션·전략·방향·동작을 유지해야 합니다.

상태: acknowledged(접수), submitted(주문 제출), partially_filled(부분 체결), filled(체결), rejected(거부), cancelled(취소), protection_updated(보호가격 반영), error(오류).

체결 보고의 qty는 그 한 번에 새로 체결된 BTC 수량입니다. 누적 수량·원주문 수량이 아닙니다. fill_price는 그 체결의 실제 가격이고, fill_id가 필수입니다. 여러 부분 체결은 서로 다른 report_id/sequence/fill_id로 보냅니다. 같은 fill_id를 새 report_id로 중복 보고하면 409로 거부됩니다.

체결 외 상태에서는 qty, fill_price, fill_id를 모두 null로 보냅니다. 보호가격 반영은 action:protection_update로 보내고 바로 최신 스냅샷을 뒤따르게 합니다. reason_code는 정리된 코드만 사용하며 계정정보가 포함될 수 있는 거래소 오류 원문은 넣지 않습니다.

B. 실제 전체 포지션 — kind: snapshot

complete:true, account_scope:lake_dedicated_BTCUSDT를 명시합니다. 이 범위는 lake 전용 계정의 BTCUSDT 전체 포지션이며 다른 계정·종목까지 비어 있다는 뜻은 아닙니다. 기본·과열·횡보 몫을 모두 포함하고 전략별 합계와 거래소 실제 수량을 대사한 뒤 보내야 합니다.

타 전략과 공유하는 계정이거나 귀속이 불확실하면 complete:true를 보내지 마세요. 현재 수신기는 그러한 불완전 스냅샷을 거부하고 미확인 상태를 유지합니다. 수신기는 상대의 확인 자료를 기록하며 Bybit에 직접 접속해 진위를 재검증하지는 않습니다.

포지션별 qty는 잔여 BTC 수량, entry_price는 실제 평균 진입가입니다. mark_price는 Bybit 마크가격 또는 null, stop_loss는 확인된 손절가 또는 null입니다. take_profit:null은 미확인, []는 익절 주문이 없다고 확인됨, 가격 배열은 현재 확인된 익절 가격들입니다. 누락 값을 0으로 대신하지 않습니다. 각 updated_at_ms는 스냅샷 관측 시각 이하여야 합니다.

Bybit의 positionIdx=0은 단방향, 1은 헤지 롱, 2는 헤지 숏입니다. 한 스냅샷에서 단방향과 헤지 모드를 섞지 않습니다. 단방향에서 서로 반대 방향 몫을 동시에 보고할 수도 없습니다. 같은 position_id는 한 번만 포함합니다.

5. 대시보드가 “실제 포지션”을 판단하는 기준

상태표시 의미
미연동 / 확인 대기LIVE 키 또는 완전한 스냅샷이 없음. “포지션 없음”이라고 추정하지 않음.
최신 확인완전한 LIVE 스냅샷의 관측 시각이 90초 이내이고 순서 누락·후속 체결 미대사가 없음.
보유 없음위 조건을 만족하면서 전체 positions가 빈 배열일 때만 확인됨.
갱신 지연마지막 전체 스냅샷 관측이 90초 초과. 과거 잔량을 최신으로 표시하지 않음.
불일치sequence 누락 또는 체결·보호가격 변경 뒤 전체 스냅샷 미수신. 회신 누락 뒤 다음 연속 번호의 완전 스냅샷으로 현재 잔량을 다시 확인. 빠진 과거 체결 기록은 별도 대사 필요.

조회 응답의 positions는 현재 정합성이 확인될 때만 반환합니다. 지연·불일치 상태의 지난 자료는 last_known_positions와 last_snapshot_observed_at_ms / last_snapshot_received_at_ms에 별도 보관합니다. positions_known은 현재 확인 여부이고 flat:null은 알 수 없다는 뜻입니다. 표시용 최근 체결 30건과 별도로 마지막 잔량·보호가격 변경 순서를 영속 추적하므로 오래된 미대사 체결이 목록에서 빠져도 정상으로 바뀌지 않습니다.

체결 한 건만으로 포지션 잔량을 임의 계산하지 않습니다. 잔량이 0이라고 보이려면 실제 전체 스냅샷이 와야 합니다. 체결·손절·익절 확인과 백테스트 계산은 분리되며 비용 반영 수익률을 이 수신기에서 계산하지 않습니다.

중복·순서·실패 처리

  • 같은 report_id + 같은 원본 본문은 200 duplicate:true. 최초 영속 접수는 202. 둘 다 기록 접수일 뿐 주문 실행을 뜻하지 않습니다.
  • 같은 ID의 다른 본문, 이미 처리한 sequence 또는 관측 시각 역전, 새 report_id로 보낸 중복 fill_id는 409. 자동 우회·번호 덮어쓰기를 하지 않고 원장을 대조합니다.
  • 400 형식·의미 오류, 401 서명·시간 오류, 403 Origin/Host 오류, 413 본문 크기 초과, 415 형식·압축 오류, 503 키 미설정·저장 실패입니다.
  • 자동 재시도는 설정하지 않았습니다. 재시도 정책을 합의할 경우 60초 인증 허용 시간 안에 같은 원본 본문·ID·sequence를 유지해야 합니다. 같은 ID의 ts만 바꾸면 충돌합니다. 시간 초과 후 접수 여부가 모호하거나 60초가 지났으면 먼저 대사합니다.
  • 예전 ZigZag의 “0.5초 후 1회 재시도”는 현재 lake에 자동 승계되지 않습니다.

6. 기록 전용 검증 순서

  1. 양쪽을 TEST 모드로 준비하고 주문 실행을 차단합니다. 공개 주소·인증·보고 범위를 확정합니다.
