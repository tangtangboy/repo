웹훅 수신 안내

상대 서버가 매매 신호를 받기 위한 준비 사항입니다. 기존 대화의 웹훅 규격과 lake 전략에 필요한 추가 협의를 구분했습니다.

현재 상태: lake 웹훅 미연동 · 실제 발송 0 · 자동 재시도 미설정

먼저 수신 내용을 저장하는 테스트를 진행합니다. 이 단계에서는 주문을 실행하지 않습니다.

기존 대화에서 확인된 규격

아래는 첨부된 ZigZag 푸시 방식 v1.0의 규격입니다. lake의 최종 계약은 아직 확정되지 않았습니다.

항목기존 규격
전달 방식발신 서버 → 상대 HTTPS 수신 주소로 POST. Content-Type: application/json.
서명 헤더X-Signature: 공유 시크릿과 수신한 원본 본문 바이트로 계산한 HMAC-SHA256의 16진수 값. JSON을 다시 직렬화한 뒤 검증하면 안 됩니다.
시간 헤더X-Timestamp: Unix 밀리초, 본문 ts와 동일. 현재 시각에서 ±60초 밖이면 거부하도록 권장돼 있습니다.
응답정상 접수 시 5초 안에 2xx 반환. 응답 본문은 무관합니다. 접수 응답은 실제 체결 확인이 아닙니다.
재시도기존 시스템은 비2xx 또는 시간 초과 시 0.5초 뒤 1회 재전송. 이 설정은 현재 lake에 적용돼 있지 않습니다.
중복·순서trade_id + event로 중복 처리를 막습니다. 같은 심볼은 open → close 순서, 서로 다른 심볼 간 순서는 무관합니다.
open해당 심볼·방향의 신규 진입과 sl_price 손절 설정. 기존 계약은 심볼당 한 방향 포지션을 전제로 합니다.
close해당 심볼 전량을 reduceOnly 시장가로 청산하는 뜻입니다. 부분 익절로 해석하지 않습니다.
test본문 파싱과 서명 검증용입니다. 매매를 실행하지 않습니다.
본문 필드event, bot, trade_id, symbol, direction, entry_price, sl_price, reason, pnl_pct, ts. 이벤트에 따라 포함 필드가 다릅니다. 가격·손익 참고값은 상대 계정의 체결·실현손익이 아닙니다.

마지막 첨부의 “6건 모두 HTTP 200”은 ZigZag 두 스트림에서 test → open → close를 확인한 당시 기록입니다. lake 연결 완료나 현재 수신 서버의 정상 동작을 입증하지 않습니다.

lake용 추가 협의안

아래 항목은 아직 상대와 합의되지 않은 제안입니다. 기존 close에 부분 익절을 그대로 넣으면 전량 청산될 수 있어, 연결 전에 의미를 맞춰야 합니다.

맞출 항목협의안
매매 동작entry / add / partial_exit / full_exit / protection_update로 신규 진입·추가 진입·부분 청산·전량 종료·손절 등 보호가격 변경을 구분합니다.
신호 식별재전송해도 같은 event_id를 사용하고 영속 저장합니다. 기존 trade_id + event만으로는 반복되는 추가 진입과 부분 청산을 구분할 수 없습니다.
포지션·순서position_id, 롱·숏 구분, 포지션별 증가 sequence를 둡니다. 누락·순서 역전 시 처리를 합의합니다.
수량변경 수량·단위·처리 후 기대 잔량을 명시합니다. 비율을 쓴다면 최초 수량 대비인지 잔여 수량 대비인지 확정합니다.
헤지·손절 변경롱·숏을 함께 보유하는 헤지 지원 여부와 레그 구분을 확인합니다. 손절 변경의 버전과 적용 확인도 맞춥니다.
전략·처리 결과표시 이름과 별도로 안정된 전략 ID·규격 버전을 정합니다. 신호 접수, 주문 제출, 체결, 거부는 별도 상태로 기록합니다.

상대에게 받을 세 가지

  1. 테스트용 공개 HTTPS 수신 주소. 기존 서버에서 lake를 구분할 경로 또는 전략 등록 방식, 발신 IP 허용 목록 필요 여부도 알려주세요.
  2. 공유 시크릿을 안전하게 전달할 방법. 실제 시크릿은 이 안내서·화면·일반 로그에 기재하지 않습니다.
  3. 추가 규격 지원 여부. 추가 진입, 부분 청산, 헤지, 손절 변경, 고유 이벤트 ID와 순서 처리를 지원하는지 회신해주세요.

기록 전용 테스트 순서

  1. 상대 수신기를 기록만 하고 주문하지 않는 상태로 준비합니다. 신호 규격, 접수 기준, 실패 시 동작을 먼저 합의합니다.
  2. test로 파싱·원문 서명·시간 검증을 확인합니다. 잘못된 서명과 만료된 신호는 거부되는지 확인합니다.
  3. 합의된 예시로 신규 진입 → 추가 진입 → 부분 청산 → 손절 변경 → 전량 종료를 기록하고 양쪽의 결과를 대조합니다.
  4. 같은 신호 재수신, 순서 역전, 누락, 잘못된 수량, 헤지의 롱·숏 구분을 검증합니다. 중복이 새 매매로 처리되면 통과가 아닙니다.
  5. 수신 검증 후 발송 시작 시각·중지 방법·재시도 정책을 별도로 확정합니다. 실제 발송은 별도 승인 후 미래 신호부터 시작하며 차트의 과거 재구성 신호는 보내지 않습니다.

상대방에게 전달할 요청문

lake(가명) strategt 시그널의 웹훅 수신을 준비하려고 합니다. 기존 ZigZag 수신 규격을 참고하되, 우선 주문 없이 기록만 하는 테스트로 진행해주세요. 테스트용 HTTPS 수신 주소, 공유 시크릿을 전달할 안전한 방법, 추가 진입·부분 청산·헤지·손절 변경과 고유 이벤트 ID·순서 처리 지원 여부를 알려주세요. 기존 close는 전량 청산이므로 lake의 부분 익절과 구분하는 규격을 먼저 맞추고, 테스트 기록을 서로 대조한 뒤 실제 발송을 별도로 결정하겠습니다.

근거: 사용자 제공 첨부의 ZigZag 푸시 방식 v1.0 및 마지막 연동 완료 메시지 직접 확인. 실제 주소·IP·시크릿·개인 이름은 모두 생략했습니다. 기존 전략의 사이징·레버리지·고정 손절 수치는 lake에 이관하지 않았습니다. 이 안내서 작성 중 외부 발송이나 수신 서버 접촉은 수행하지 않았습니다.
